- Commands: `/spec`, `/build`, `/ship` — orchestrate the persona agents into an idea-to-release pipeline; `/ship` fans `code-reviewer` and `security-auditor` out in parallel, merges into a go/no-go, and hands off to `release-manager` on go

- `AGENTS.md`: "Idea-to-Release Pipeline" section describing the `/spec` → `/build` → `/ship` flow and when to invoke a persona agent directly instead of via its command
- `comment-check` tool: `PostToolUse` reminder when an edit adds a new non-Doxygen comment to a C++ file, pointing back at the `comments` skill — runs unconditionally, unlike the lint tools which require a project config file
- `review-publish-guard` tool: `PreToolUse` `permissionDecision: ask` before a `gh` command that publishes review feedback the moment it runs — `gh pr review --comment/--approve/--request-changes`, `gh pr comment`, `POST /pulls/{n}/comments` with `in_reply_to`, an `event` field on `POST /pulls/{n}/reviews`, `submitPullRequestReview`, and `addPullRequestReviewThreadReply` without a `pullRequestReviewId`, which belongs to no pending review and therefore publishes. The prompt names the pending-review alternative, and the pending path itself (`addPullRequestReview` with no `event`, `addPullRequestReviewThread`, a reply carrying the review id, `deletePullRequestReview`, `gh api graphql --input`) runs unprompted. Rules read a command as argv rather than as text: each rule anchors to the command word, so a commit message or progress note naming a blocked command does not prompt, and a quoted body arrives as one token, so a delimiter or a flag quoted inside it neither splits the call apart nor changes how it parses. Enforces `pr-rules` → Pending by Default, which until now held only while the agent remembered it

- Skills: `github-cli` and `gitlab-cli` — the platform mechanics behind the process skills. `github-cli` carries the `gh` commands for issues, pull requests, labels, the pending review cycle, and a `--no-ff` merge, each marked verified or untested, plus the five traps the CLI help does not state. `gitlab-cli` carries the `glab` equivalents, verified end to end against glab 1.105.0 on gitlab.com: issues, merge requests, the draft-note cycle, `bulk_publish`, and a merge under `merge_method=merge`. It records the ways the CLI misleads, each caught by running it: `glab api` has no `--jq` flag, `position[...]` bracket fields are accepted and silently dropped so an inline finding lands as an overall comment, `--input` without an explicit `Content-Type` answers `415`, `@<path>` expands to the file's contents only under `-F` while `-f` stores the path itself, a stale `head_sha` is not rejected but silently overwritten with the MR's current head, and `glab mr note --message` is deprecated in favour of `glab mr note create`. Neither skill states policy: what a PR must contain and whether feedback may be published stay in `pr-rules` and `issue-rules`
- `/review-loop` command: iterates review → fix → re-review until a pass reports no blocking finding, capped at 3 passes. The tool(s) and scope come from the call (e.g. `code-reviewer` + `security-auditor` in parallel, the same pair `/ship` runs once) — the command asks rather than guessing when no tool is named, since the tool decides what counts as blocking. Depth is a fixed, tool-agnostic scale (`quick`/`light`/`normal`/`thorough`/`ultra`, defaulting to `normal`) translated into whatever the named tool's own notion of depth is, so the same word means the same relative rigor no matter which tool answers it. Each pass runs in the current checkout when it already matches the requested scope and holds nothing the review would disturb, or in an isolated worktree otherwise (falling back to a stash-and-review-in-place when the scope is the same branch already checked out, since git won't check out one branch into two worktrees), removed once the loop ends and every fix is committed. A blocking pass gets fixed and re-reviewed; nits and questions are resolved along the way when practical instead of being left open by default. Reaching the cap still blocking is reported as "not converging" rather than claiming success. Every run ends with one summary — found, fixed, still open — not just a verdict. `git push`, `gh issue edit`, `gh pr edit`, and merge stay gated on user confirmation the same as everywhere else — the loop fixes code, it does not publish or merge on its own

- `skill-gate` now enforces its notice instead of only speaking it. The first `Edit`/`Write`/`MultiEdit`/`NotebookEdit` on a file whose claiming skills are not loaded is denied, with the notice and a retry instruction as the reason, so loading the skills becomes the shortest path to the edit; a repeat of the same file and missing-skill set in the same session downgrades to the warning, so an agent that cannot invoke the Skill tool loses one attempt, never the task. The gate also covers the shell detour around a blocked edit: a `Bash` command writing to a claimed file through a redirection, `tee`, `Set-Content`/`Add-Content`/`Out-File`, or a `cp`/`mv` destination passes the same deny-once check with the same session state. Writes through interpreters (`node -e`, `python -c`) stay out of reach — the gate narrows the bypass, it does not seal it

- `statusline` tool: renders the line under the prompt as `[Opus 5 (1M context)] [effort high] [Context 34%] [5h 42% 2026-08-07T14:12] [7d 61% 2026-08-10T16:00] [main]`, entirely from the payload Claude Code writes to its stdin — no API call and no transcript parsing. `Context` and the two rate-limit windows are coloured by how full they are (green below 60%, yellow to 84%, red from 85%), each limit stating in local time when it resets; the model, effort and branch badges are dim, and a badge the payload cannot supply is left out: the rate-limit windows appear once the API has returned its usage headers, the branch only inside a repository, read from `.git/HEAD` rather than by spawning `git` on every render, with control bytes stripped and the length capped so a crafted HEAD cannot write escape sequences into the terminal. Installing takes over the single `statusLine` slot: `install.js` records whichever command was registered before and `uninstall.js` puts it back
- The statusline keeps whatever the displaced `statusLine` command drew, in front of its own badges. Claude Code registers one such command, so a plugin's statusline would otherwise disappear on install; the command string install recorded is all the tool knows about it — no path, no file, no plugin name — and uninstall hands the slot back untouched. That command never runs while the line is being rendered: each render prints the text the previous run cached and, once that text is older than two seconds, leaves a detached process behind to refresh it, so a command taking a third of a second costs nothing per keystroke and its badge trails by one render at most. A failing or slow command leaves its text absent and changes nothing else

### Changed

- Every guarded tool call now waits on one process instead of one per guard. The checks in front of a shell command — destructive commands, banned commit trailers, review publishing, secrets, the skill gate — run inside the dispatcher, so the pause no longer grows with the number of guards, and every decision, warning and block stays the one it was. A guard whose file is missing, broken, or still written to the old stdin/stdout shape costs only itself: it is skipped with a line on stderr and the rest decide as before. A `PreToolUse` tool of your own now exports `verdict(payload)`, and one left in the old shape is skipped that same way, so it stops guarding without failing loudly

- The global `CLAUDE.md` no longer restates the skill list and its triggers, and the session-start check that policed that copy against `skills/` is gone with it. The reminder injected on each prompt is generated from the same frontmatter that decides how a skill is triggered, so it cannot fall behind. A subagent never sees that reminder: the skills its persona in `agents/` names are the only list it starts from, and a skill tied to a kind of file is announced when that file is edited rather than on every prompt

- `CONTRIBUTING.md` no longer carries a branch pattern and a commit-type list that contradict `commit-rules`, nor a five-step recipe for adding a skill that left it reaching no agent at all - the template it started from ships an opt-out from the every-prompt reminder and a placeholder path glob, and the recipe named neither. Each rule now comes from the file that owns it, and the order of work from `pr-rules` -> Workflow and the lifecycle map rather than a third partial account. `README.md`'s manual setup installs what `node install.js` installs and names what it cannot cover: nothing is backed up, and `uninstall.js` has no record to reverse. The git pre-commit hook is stated to apply to this checkout alone

- The development lifecycle was stated twice along axes that never referenced each other — `pr-rules` → Workflow's seven steps, and `AGENTS.md`'s pipeline of commands and personas — so nothing said whether `/build` is step 3 or steps 2 to 4, or where planning and release sit. `AGENTS.md` → Idea-to-Release Pipeline now carries a lifecycle map: one row per stage against the seven steps, the `issue-rules` state the issue is in, and the skills that apply there. Both ends are on it, and a stage no command or persona covers says so rather than naming the nearest one; `pr-rules` → Workflow points at it

- A dot-file or dot-directory is now ignored unless `.gitignore` names it as one this repository tracks. Every tool, editor and agent runtime leaves one behind, and each had to be noticed and added by hand before `git status` was quiet again; an untracked directory nobody has got round to sits next to a file that genuinely should have been committed, and trains the reader to skim past both

- `pr-rules` and `issue-rules` skills: the platform commands moved out into `github-cli` and `gitlab-cli`, leaving each rule stated in exactly one place. The process skills keep the rules and point at the platform skill for the command; a `gh` or `glab` change no longer means editing rules that are not about a CLI, and every other consumer of the same commands reads them from one file

- `pr-rules` skill: an agent no longer publishes its own review feedback on any platform. Where a draft mechanism exists (GitHub pending reviews, GitLab draft notes, Gerrit drafts) the feedback waits there for a human to submit; where none exists (Jira and most trackers, chat, email) nothing is posted at all and the wording goes to the human instead. An explicit instruction naming the act is the only exception; `gh pr review`, `gh pr comment`, and REST `in_reply_to` are banned for review feedback, while the issue comments the Workflow requires stay unaffected. The GitHub cycle and its four non-obvious traps, plus the GitLab equivalent, live in `pr-rules` → Pending by Default
- `pr-rules` skill: Merge Strategy states that the human authorises each merge, matching the rule that review feedback already follows

- `AGENTS.md` "Adding a skill": states that `install.js` copies only `skills/<name>/SKILL.md`, so a skill stays one file until that copy loop changes
- `api-design`, `doxygen` and `encapsulation` skills renamed to `cpp-api-design`, `cpp-doxygen` and `cpp-encapsulation`, and each description now names C++. Every rule in the three is C++-only (`#pragma once`, `void*`, `friend`, Doxygen tags), so the neutral names presented them as the skills to load when designing an API or documenting an interface in any language. `AGENTS.md` "Adding a skill" states the convention and the test a reviewer applies: a skill whose rules cannot be restated for another language carries the language as a prefix. `comments`, `ddd` and `hook-scripts` keep their names — the first two state language-neutral rules that only use C++ in the examples, and `hook-scripts` is bound to a tool rather than a language
- Re-running `install` after a rename now also hands back a path the previous install overwrote rather than created, restoring the content it had before, so a retired skill stops loading at upgrade time instead of only at uninstall. When the backup that held the original is gone, install releases the path — naming it and leaving the file as it is — instead of keeping a record that `uninstall` can only fail on, which used to leave every later uninstall exiting with an error over one path the repo no longer ships. `config/retired.json` lists those paths; install names any that survive untracked and leaves their removal to the user, since an untracked file may be one the user wrote
- Every skill pair that can fire on one task audited for a rule stated on both sides, and the result written down as a skill ownership map in `AGENTS.md`: one line per skill naming the concern it owns and what it hands off, which is what "Adding a skill" step 0's overlap check now reads from instead of a reviewer's memory. Each duplicate found is now stated once and referenced from the other side. `#pragma once` lives in `cpp-coding` → Header Guards, together with the C++20 module exception `cpp-api-design` carried separately. `cpp-api-design` → Breaking Changes keeps the definition of "breaking" and hands the bump to `release`, the entry to `changelog`, and deprecate-before-removal to `deprecation-and-migration`. `release` Step 2 no longer restates the `[Unreleased]` rename, which had already drifted — its copy was missing the fresh `[Unreleased]` section `changelog` → On Release requires — and `release`'s two overlapping verification lists merged into one Step 4 — Pre-Release Checklist. `issue-rules` → Types hands the type vocabulary to `commit-rules` and keeps only the capitalization difference, its own copy having lost `submodule updates` from `Chore` and narrowed `Fix`. `code-review-and-quality` → Giving Feedback hands finding wording to `pr-rules` → Review Comments and keeps what counts as a finding. `cpp-testing` and `security-and-hardening` hand regression-test timing and reproduce-then-root-cause order to `debugging`; `hook-scripts` hands the shape of a tool's test to `node-testing`. `test-driven-development` pointed at `cpp-testing` for structure, naming and coverage on every task including a JS one, and now names the testing skill of the language being written. `cpp-testing`/`node-testing` and `github-cli`/`gitlab-cli` keep their parallel statements: no task loads both halves of either pair, so the map records that duplication as deliberate rather than routing a JS test task through a `cpp-` skill for one line
- `commit-rules` skill: the commit body is now capped at one short paragraph (2-6 lines) explaining why the change is made this way. The section previously listed three things to explain with no limit, and bodies grew into second PR descriptions — file-by-file bullet lists, `## Motivation`/`## Changes` headers, pasted benchmark and CI output, enumerated rejected alternatives — restating the diff and burying the one thing only a commit can carry. Evidence, measurements, alternatives considered, migration notes and test plans are now named as belonging to the PR description; only content that has to travel with the commit itself, a `BREAKING CHANGE:` paragraph or an issue trailer, may follow the explanatory paragraph
- `writing-style` skill: added "State the Result, Not the Process". Every artifact now states the state it leaves behind, leaving out the order the work happened in, abandoned attempts, corrections and the mistakes behind them, and the deliberation that produced an approach rather than the constraint that decided it. Length counts as correctness: text longer than its subject requires spends the reader's attention before they reach the part that matters. The rule covers every channel, not only the artifacts with a template — documentation, commit bodies, issue and PR/MR descriptions, comments and replies in an issue or review thread, progress notes, and tracker, chat or mail messages on any platform
- `writing-style` skill: added "No Figures That Go Stale". Numbers measuring a run rather than describing the subject — test totals and pass counts, coverage percentages, timings, counts of changed files, lines or commits — are left out of every artifact, since a rebase or one further commit invalidates them silently while the CI run and the diff hold the current values. The durable reference takes their place: the command that produces the number, the test that covers the behaviour, or the file and symbol that changed. A figure belonging to the subject itself stays, such as a measured regression the change exists to fix or a documented limit; a measurement that needs the code it was taken on names a released version, a tag, or the merge commit on the protected branch, never a hash from the branch under review, which rebase replaces. The `AGENTS.md` ownership map now names both new concerns on the `writing-style` line, and records that each artifact's own length budget stays with that artifact's skill — the commit body's paragraph in `commit-rules`, the PR description's per-section budget in `pr-rules`
- `pr-rules` skill: the description now carries a per-section length budget — Problem up to five lines, Summary up to five one-line bullets, Implementation up to six bullets each naming a file or symbol, Test plan one line per item naming the command or test. A change too large for the budget is a PR to split rather than a description to extend, and what the description must leave out is stated once in `writing-style` → State the Result, Not the Process
- `PreToolUse` dispatcher now emits one permission decision per run: the strictest of the decisions returned (`deny` over `ask` over `allow`), carrying every reason behind it and any warning printed alongside. Two tools deciding on one command (`git push && gh pr comment ...`) used to write two JSON objects onto one stdout, which parses as neither, so the decision could be lost together with the prompt it was raised for; the reason is also all the user reads before answering, and one tool's reason alone misstates what is about to run

### Fixed

- A persona agent now loads the skills it names. Each of the five carried a list of skills to apply and no `Skill` tool to load them with, so what it actually followed was the abridged copy of those rules in its own definition — a copy that drifts from the skill it paraphrases, and the only version the persona ever saw. Every persona now carries the tool, names the skills and the order to load them in, and leaves the rules to be read where they are stated
- The `Stop` notification now waits for a call started in the background, instead of announcing the turn complete while that call was still running. The counter behind the deferral was keyed on the tool name `Agent` while looking for `run_in_background: true`, a field no agent call carries, and the shells that do carry it were routed elsewhere, so the count never left zero and the deferral never took effect. A background call is now counted from what its payload carries, whichever tool made it, and counted once it has started rather than when it is asked for, so a call refused at any gate is not waited for
- `uninstall` now removes this repository's hooks from `settings.json` even when they were already registered there before `install` ran. Such a hook was left unrecorded, and stayed unrecorded through every later reinstall, so `uninstall` reported success while leaving every dispatcher hook live and the only way out was editing `settings.json` by hand. `install` now claims a hook command it ships whether or not it was already in the file, without duplicating the entry, since that command launches a dispatcher uninstall removes. A machine in that state recovers by re-running `node install.js`
- `install` now backs up every file it overwrites, and `uninstall` restores it byte for byte. A skill, tool, hook, agent or command the user already kept under `~/.claude/` at a name this repository also ships was replaced with no backup taken and no record kept, so the user's only copy was gone and `uninstall` could not bring it back. `settings.json` stays the exception: it is merged rather than replaced, and reverted by subtracting only what install added
- The command guards now read a command as argv instead of matching its text, so a rule catches every spelling of the call it names. `bash-safety` let `git -C <dir> push`, `git -c <name>=<value> push` and `git --git-dir=<path> push` reach the remote unprompted, and `sudo git push`, `env VAR=x git push`, `(git push)`, `$(git push)`, `bash -c "git push"`, `powershell -EncodedCommand <base64>`, a `node -e` script calling `execSync('git push')` and an aliased `git p` with them; `-C <dir>` is the common form when pushing a submodule from the superproject root, and under `bypassPermissions` the hook is the only gate. `commit-trailer-guard` had the same hole and let a banned AI-attribution trailer through behind `git -C <dir> commit`. `tools/shell-lex.js` lexes a command into the argv of every command it runs — transparent prefixes dropped, a quoted argument kept as one token, and an interpreter's own argument read as a command string in its own right, up to three quoting levels deep — and `tools/git-command.js` reads that argv as a git call with the global options skipped, in both the separated and the attached form (`-C <dir>` and `-Cdir`), and any alias resolved to the subcommand it stands for, whether defined with `-c alias.x=…` or in a git config file. `skill-gate` reads its command position from the same lexer rather than from a copy of it. The `rm`, `rmdir`, `format`, `del` and `Remove-Item` rules moved to argv as well, which fixes the inverse defect the text matching carried: a destructive command named inside a quoted argument no longer counts, so `gh issue comment -b "... never run rm -rf / ..."` is not blocked and a command whose name merely ends in `git` no longer warns. The SQL warnings stay on the raw text, since `psql -c "DROP TABLE users"` carries its subject inside the quotes. A command is recognised however its name was spelled — `/usr/bin/git push`, `git.exe push` and a quoted path carrying a space all count as `git` — and `rm -rf /*` blocks like `rm -rf /`, the form that gets past a shell refusing to remove the root itself. A subcommand a rule does not name stays unaffected: `git -C <dir> status` does not prompt
- `secret-guard` now reads shell commands as well as file writes, so a private key, AWS key or GitHub PAT written through `echo`, a heredoc, an `export`, or passed as a curl header is blocked before it runs. It sat on the write guards alone, where a command carrying the same secret reached the system unchecked
- `PostToolUse` now runs after a write by any tool, not only the four it names. `comment-check` and the configured lint tools sat behind a `tool_name` check, so a file written by a plugin's edit tool or an MCP server was never formatted, linted, or checked for a new comment, and nothing said a check had been skipped. The trigger is the payload: a path arriving with the content written to it, or one of the four edit tools naming a path with no content field. The name check stays for that second case rather than as a shortcut — `Read` carries `file_path` too, and formatting a file that was only read would rewrite it. `comment-check` reads the target from `path` and `notebook_path` as well, so a write naming its file in either of those no longer arrives with an empty path and silently produces no reminder. Files written by a shell command remain out of reach: the lint tools take one path as an argument while a command can write several
- `PreToolUse` now routes guards by payload instead of by tool name, so every tool running a command is checked. The dispatcher keyed its guard list on `Bash` alone, and the PowerShell tool — the primary shell on Windows — reached the system unchecked: `git push` ran without the confirmation prompt, a commit carrying a banned AI-attribution trailer passed `commit-trailer-guard`, `gh pr comment` and `gh pr review` published review feedback without the `review-publish-guard` prompt, and a write through `Set-Content`/`Out-File`/redirection skipped `skill-gate`. Any other shell, an MCP server exposing one, or a plugin's own edit tool escaped the same way, and silently, since an unknown name makes the dispatcher exit 0 while the guards still look installed. A `command` string now reaches the command guards and a write target arriving with its content reaches the write guards, whatever the tool is called, and a payload carrying both reaches both sets; `skill-gate` decides the same way, taking the targets of the command and of the declared write together, and reads `notebook_path`/`new_source` as a write target as well. `tools/payload.js` holds the rule for the tools while the dispatcher states it for itself — requiring a file from `tools/` would throw on every tool call once that file went missing — and `test/payload.test.js` runs both copies over every payload shape so the pair cannot drift. The shipped `ask` list gained `PowerShell(git push *)`, with a test holding every shell rule in it to both named tools. `hook-scripts` and `AGENTS.md` state the rule and its deliberate cost: a tool whose `command` field is not a shell command reaches the command guards too, which is a prompt, against an unchecked `git push` in the other direction

- `skill-gate` reads a Bash command as argv rather than as text when looking for the file a command writes. The write forms were regexes over the raw command string, so prose inside a quoted argument gated the call: `gh issue comment --body "... the gate denied tee a.cpp b.cpp ..."` was itself denied, and every such mention burned one deny and added noise the reader learns to ignore. A quote-aware lexer now makes each quoted argument one opaque token, recognises `tee`, `cp`/`mv` and the PowerShell content cmdlets only in command position (start of the command, after `|`/`;`/`&`/`$(`, behind a `VAR=x` prefix — quoted value included — or behind a transparent prefix such as `sudo`, `xargs`, `nohup`), and takes redirection targets only from a `>`/`>>`/`>|` outside quotes — a quoted target (`> "my file.cpp"`), multi-file `tee`, descriptor redirections and the flag forms keep their previous behaviour, a `>&2` between operands no longer hides the operand after it, and `man tee a.cpp` no longer counts as a write

- `comment-check` no longer reads the `/*` or `/**` inside a string as a comment opener. The line openers (`//`, `#`, `--`, `;`, `%`) already had to sit at line start or after whitespace, but the C-family block opener carried no such anchor, so an edit adding a glob such as `"**/*.cpp"` — common in skill `paths:` fixtures — was reported as a new comment on every such line, and a reminder that fires on non-comments trains its reader to ignore it. The unanchored doc openers (`///`, `//!`, `/**`) had the inverse defect: a `/**` inside a glob string marked the whole line as a doc comment and hid a real `//` comment sitting next to it. Every opener now takes the same anchor; a genuine trailing block comment (`int x = 5; /* meaning */`) is still caught

- A tool naming a permission decision outside `allow`, `ask` and `deny` no longer decides anything. Those three are the whole vocabulary, and an unrecognized value used to rank as low as `allow`, so a tool bug could win the merge against a real `allow` and reach Claude Code as a decision it cannot act on. Such output now counts as text, behind a line naming the tool it came from: it still reaches the user — inside the reason when another tool decides, on its own when none does — while the decision comes from a tool that named one. Naming the tool is what makes the run's stdout unreadable as a decision even when that malformed output is the only thing a run produced, and points at the tool to fix

- A permission prompt no longer carries a line reading `undefined`. The `PreToolUse` dispatcher merges the reasons behind every decision into the one prompt the user answers, and a tool that decides without stating a reason used to contribute the literal string `undefined` to that text — `permissionDecision` alone makes a response a decision, so the reason is optional to the tool and was mandatory to the merge. A decision without a reason now contributes no line. No shipped tool omits its reason, so the defect was latent and would have surfaced with the next tool to emit a decision

- A warning from a `PreToolUse` or `PostToolUse` hook now reaches Claude. Both dispatchers wrote plain text to stdout, which Claude Code adds to the model's context only on `UserPromptSubmit`, `UserPromptExpansion` and `SessionStart` — everywhere else it goes to the debug log. Every warning these hooks produced was therefore invisible to the agent it was written for: the `skill-gate` notice naming the skills an edit needs, the `comment-check` reminder, and `clang-tidy`, `cppcheck` and `secret-guard` output. They now travel in `hookSpecificOutput.additionalContext`, and a permission reason still repeats the warning for the user, who reads it in the prompt and nowhere else. `skills/hook-scripts/SKILL.md` documented the channel backwards, which is what produced the defect; its exit-code table is corrected and a "Reaching the Model" section states which event carries what

- The `skill-gate` notice now orders every named skill loaded instead of listing candidates. The old wording — "load with the Skill tool before editing — comments, …" — read as a reminder of options, and a delivered notice was answered by loading only the skills the model judged relevant: in one live session a notice naming four skills produced Skill calls for two of them, and `comments` was skipped in 21 delivered notices in a row because its description reads as conditional. The notice now states that the path match itself is the trigger, that each named skill must be loaded, and that none may be skipped as irrelevant

- `comment-check` covers every language, not only C++. It knew five C++ extensions and the `//` and `/* */` openers, so an edit adding a comment to a hook script, a Python module, a shell script or a build file produced no reminder at all. A syntax table now maps an extension, or a name like `Makefile`, to the openers of its family — `//`, `/* */`, `#`, `--`, `;`, `%` and `<!-- -->` — counting one only at line start or after whitespace, so `https://x`, `#ffffff` and `counter--` stay code. The `comments` skill matches: it declares those extensions in its `paths`, so the edit-time gate names it on any source file instead of only alongside `cpp-coding` and `hook-scripts`, and its scope line names the markers rather than a language. A `paths` glob accepts brace alternatives (`**/*.{py,sh}`) so one line covers a language family, and matches case-insensitively, so `Makefile` and `makefile` reach the same skill
